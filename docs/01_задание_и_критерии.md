# 01. Задание и критерии

Tachyon - многопользовательский трекер финансов: ведение доходов и расходов,
лимиты бюджета по категориям, повторяющиеся операции и прогноз трат на конец
месяца, всё это через REST API. Регистрация и вход, изоляция данных между
пользователями, экспорт отчёта за период в Excel или PDF. Стек: Python,
Flask/FastAPI, SQLAlchemy + SQLite, pandas, APScheduler, pytest.

Сроки: сегодня 5 октября 2026 (понедельник), сдача кода 22 октября (четверг),
защита 24-25 октября. На разработку 18 дней, команду из 5 человек.

## 1. Функционал по пунктам ТЗ

| Пункт ТЗ | Что значит на практике | Как проверим |

## 3. Три вещи, которые проверят в первую очередь

В ТЗ прямо сказано: «корректность логики (прогноза) и расчётов за неполный
месяц или нулевые траты, изоляция данных между пользователей, качество
тестов». Это ровно три вещи, которые жюри открывает первой. Ломается проект
не на красивой диаграмме, а на делении на ноль.

### 3.1. Прогноз за неполный месяц и нулевые траты

Формула прогноза фиксируется один раз и не меняется до защиты:

```
days_passed  = сегодняшнее число месяца
days_in_month = calendar.monthrange(год, месяц)[1]
days_left    = days_in_month - days_passed
rate         = fact_total / days_passed        # средние траты в день
forecast     = fact_total + rate * days_left + planned_recurring_left
```

`planned_recurring_left` - сумма ещё не созданных повторяющихся операций с
датой завтра по последнее число месяца.

Обязательные ветки поведения:

| Ситуация | Что должно вернуть API | Почему это ловушка |
|---|---|---|
| Первый день месяца, трат ещё нет | `forecast = planned_recurring_left`, `rate = 0`, поле `low_confidence: true` | Наивный код делает `0 / 1 = 0` и показывает прогноз 0 вместо плановых трат |
| Трат за месяц 0, повторяющихся нет | `forecast = 0`, `status: OK`, без исключения | Наивный код делит на `days_passed` и падает на нулевом `fact_total` при попытке посчитать процент |
| 1 расход 31 марта | `days_in_month = 31`, а не 30 | `timedelta(days=30)` от начала месяца даёт 31 день в марте, прогноз занижается |
| 28 февраля, високосный год | `days_in_month = 29` | То же через `calendar.monthrange`, а не через `dateutil` с дефолтом |
| Последний день месяца | `days_left = 0`, `forecast = fact_total`, прогноз совпадает с фактом | Проверка точности формулы: прогноз не должен «уезжать» от факта в последний день |
| Лимит на категорию, трат по ней 0 | Процент `0`, прогноз по категории 0, статус `OK` | Деление `fact / limit` даёт 0, а `fact / (fact + limit)` даёт неверный процент |

Тесты на каждую строку таблицы обязательны, минимум 6 тестов на прогноз.

### 3.2. Изоляция данных между пользователей

Правило, которое нарушается чаще всего: `user_id` берётся из тела запроса. Так
не делаем. Источник единственный - payload JWT (`sub`), декодируется в
dependency `get_current_user`, и в каждый запрос к БД попадает
`.where(Operation.user_id == current_user.id)`. В API нет ни одного эндпоинта,
принимающего `user_id` от клиента.

Что проверяет жюри и как это выглядит у нас:

| Проверка | Ожидаемый результат |
|---|---|
| Пользователь B запрашивает список операций | 0 строк, даже если у него нет ни одной операции |
| Пользователь B запрашивает операцию пользователя A по id | 404, не 403 и не 200. 403 подтверждает жюри, что операция существует, то есть утекает факт существования |
| Пользователь B удаляет операцию пользователя A | 404, запись остаётся у A |
| Пользователь B ставит лимит на категорию пользователя A | 404 или 422, лимит A не изменён |
| Годовой отчёт пользователя A | Не содержит ни одной операции пользователя B, даже с тем же `category_id` |
| Попытка SQL-инъекции в `?category=` | Валидация возвращает 422, данные не утекают |

Тест на изоляцию: одна фикстура создаёт двух пользователей, добавляет каждому
по операции, проверяет что выборка каждого возвращает только свои строки и
ровно 1 запись. Минимум 3 теста, лучше параметризованный.

### 3.3. Качество тестов

Требуется минимум 5 тестов на бизнес-логику, делаем 20-25. Тесты должны
покрывать границы, а не happy path. Обязательные группы:

- прогноз: неполный месяц, нулевые траты, первый день, последний день, февраль;
- лимиты: 0%, 79%, 80% (`WARNING`), 100% (`EXCEEDED`), 120% (`EXCEEDED`);
- повторяющиеся операции: запуск по расписанию, отсутствие дублей, остановка;
- изоляция: два пользователя, пересечение категорий;
- валидация: отрицательная сумма, сумма 0, несуществующая категория, будущая
  дата больше чем на год назад, комментарий длиннее 500 символов.

Тесты гоняются на временной SQLite в памяти (`StaticPool`,
`create_all` на фикстуре), не зависят от порядка, каждый падает с понятным
сообщением. Команда `pytest -q` даёт 100% passed, иначе код не заливается.

## 6. Задача* (бонус +10 баллов)

ТЗ: визуализация расходов по категориям (диаграмма) и уведомление при
превышении лимита. Стоит делать, потому что это 10 баллов из 110 (около 9%
максимума) при сравнительно низкой цене реализации: расчёты уже готовы в
разделе 3, нужна только форма отображения.

| Подзадача | Что делаем | Оценка |
|---|---|---|
| Диаграмма расходов по категориям | `GET /api/v1/reports/categories?date=2026-10-15` отдаёт `{category, spent, limit, percent}`, на веб-странице рисуется круговая или столбчатая диаграмма через Chart.js без серверного рендеринга | 0.5 дня |
| Уведомление при превышении лимита | При создании операции сервис сравнивает `fact` с `limit` по категории. При `fact >= 0.8 * limit` пишет `WARNING`, при `fact > limit` пишет `EXCEEDED` в таблицу `notifications` и логирует событие | 1 день |
| Показ уведомлений пользователю | `GET /api/v1/notifications` и баннер на главной странице, для просроченных записей кнопка «закрыть» с отметкой `is_read` | 0.5 дня |
| Тесты бонуса | Порог 80% и 100% на границе, уведомление не дублируется при повторном добавлении операции, чужой пользователь не видит уведомлений | 0.5 дня |

Порядок такой: сначала закрываем 40 баллов за работоспособность и 20 за
качество кода, потом 15 за функционал, и только потом бонус. Если 22 октября
бонус мешает сдать основное - сдаём без него, штрафа за отсутствие задачи*
нет.
