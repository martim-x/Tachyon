# 05. Процесс разработки

Этот документ описывает, как команда из пяти человек работает с кодом 18 дней подряд: почему выбран trunk-based подход, как называть ветки и коммиты, что такое Pull Request в нашем проекте, что ревьюер проверяет в первую очередь, что гоняет CI, когда задача считается_done, как проходят церемонии Scrum и в каком трекере лежит бэклог. Причина, по которой процесс вообще нужен, простая: за 18 дней каждый из пяти человек напишет много чужого кода и прочитает много своего. Если правил нет, через неделю половина репозитория перестанет собираться, а к защите никто не сможет объяснить, почему в отчёте суммы не сходятся.

Процесс здесь намеренно минимальный. Каждое правило ниже заведено потому, что без него мы теряем либо воспроизводимость сборки, либо знание о чужом коде, либо дедлайн.

## Почему Trunk-based, а не GitFlow

При пяти людях и трёх спринтах GitFlow съедает время на то, что не приносит фич. Сравнение по нашим же числам:

| Критерий | GitFlow | Trunk-based (наш выбор) |
|---|---|---|
| Веток на человека | 2 (feature + release) плюс общий develop | 1 короткая feature-ветка |
| Длина ветки | Недели | Меньше одного дня |
| Конфликт-бюджет | Отдельный merge develop и release | Только rebase поверх main |
| Слияние в main | Раз в спринт, большой пачкой | Несколько раз в день |
| Цена конфликта при 18 днях | Спор о том, чья версия схемы БД права | Решается за 15 минут |
| Интеграция | В конце спринта, риск «не собирается в пятницу» | Постоянная |

Длинные ветки при 18 днях - это гарантированные конфликты. Модель данных меняется в спринте 1, потом в спринте 3 приходят отчёты, которые читают её иначе, и release-бранч в это время стоит. В trunk-based конфликт случается в день, когда он ещё дешёвый.

Правила trunk-based для нашей команды:

- `main` всегда рабочий: зелёный CI и все тесты проходят, иначе merge невозможен;
- ветка живёт максимум один день, к концу дня открывается PR;
- в `main` попадает минимум 3-4 PR в день, а не один в конце спринта;
- `main` запрещён для прямых коммитов, только PR;
- тег релиза делается ровно один раз: `v1.0` на коммите сдачи 22 октября. Промежуточных тегов и релизных веток нет, поставка это код в `main` плюс поднятый стенд.

## Именование веток

Формат: `<тип>/<домен>-<короткое-описание>`. Домен соответствует модулю, чтобы по имени ветки было видно, чья это зона, и совпадало с ролью из файла 04.

| Тип | Когда используется | Пример |
|---|---|---|
| `feature/` | Новая функциональность | `feature/auth-jwt` |
| `fix/` | Исправление бага | `fix/isolation-user-id` |
| `refactor/` | Перестройка без изменения поведения | `refactor/scoped-repository` |
| `chore/` | Инфраструктура, конфиги, зависимости | `chore/ci-coverage-gate` |
| `docs/` | Документация и README | `docs/readme-run` |

Примеры под наши домены:

- `feature/limits-engine` - лимиты бюджета, домен R3;
- `feature/forecast-formulas` - формулы прогноза, домен R3;
- `feature/apscheduler-jobs` - планировщик повторов, домен R4;
- `feature/export-pdf` - экспорт в PDF, домен R5;
- `feature/dashboard-ui` - дашборд, домен R5;
- `fix/user-id-leak` - утечка данных между пользователями, домен R1;
- `chore/docker-compose` - стенд и Docker Compose, домен R4;
- `chore/pytest-fixtures` - каркас тестов, домен R4;
- `refactor/report-pandas` - вынос агрегации из роута, домен R5;
- `docs/api-openapi` - спецификация API, домен R2.

Имя ветки пишется латиницей, через дефис, без дат и номеров задач вида `task-123`: за 18 дней номера задач не помогают, а домен помогает.

## Коммиты

Один коммит - одна логическая единица. Если в описании коммита нужно слово «и», это два коммита.

В теле коммита фиксируются использованные паттерны и идея, от которой отталкиваемся, со ссылкой на раздел доков: ревьюер должен видеть замысел, а не только дифф. Тело отвечает на вопрос «что сделал автор и почему так», а не повторяет заголовок.

Формат - Conventional Commits:

```
<тип>(<домен>): <что сделано в прошедшем времени>
```

Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`.

Примеры под наш проект:

```
feat(auth): добавить выдачу JWT и refresh-токен
feat(limits): реализовать проверку лимита бюджета по категории
feat(forecast): добавить формулу линейного прогноза по среднему
feat(recurring): создать модель повторяющейся операции
feat(scheduler): запускать APScheduler-джоб по расписанию повторов
feat(export): добавить выгрузку отчёта в Excel
feat(dashboard): собрать дашборд с месячной сводкой
fix(isolation): закрыть выборку операций по user_id в отчёте
fix(validation): вернуть 422 на невалидный тип суммы
refactor(repository): вынести фильтр по user_id в ScopedRepository
test(forecast): добавить кейсы нулевого дохода и деления на ноль
chore(ci): добавить гейт покрытия в 70 процентов
docs(readme): описать запуск через docker compose
```

Запрещённые формулировки, которые ничего не сообщают:

- `fix fix final v2` - непонятно, что чинили и что было не так в первый раз;
- `wip`, `temp`, `asdf` - не доходят до `main`, squash их при merge;
- `не работает` - описание проблемы вместо изменения;
- коммит без описания - лишает возможности понять intent через полгода.

Тело коммита пишется, когда есть что объяснить: новая логика, паттерн или ссылка на раздел доков. Механическим правкам, чей замысел виден из диффа (переименование, перенос кода), достаточно строки заголовка.

## Pull Request

PR - это место, где вторая роль из файла 04 делает second touch. Поэтому к PR привязаны роли, а не только файлы.

Требования к размеру и описанию:

- меньше 400 изменённых строк, иначе ревьюится дольше 40 минут и задача нарезана неверно;
- название PR совпадает с названием ветки без префикса типа;
- описание состоит из трёх строк: что сделано, зачем, как проверить локально;
- в описании указывается ID задачи (`EP-03`), иначе нельзя проверить second touch по матрице;
- к PR назначены роли из матрицы: primary (автор) и second (обязательный ревьюер).

Шаблон описания:

```
Задача: EP-03 auth
Что сделано: выдача JWT при логине, проверка токена в зависимости
Зачем: без auth не работает ни один эндпоинт с пользовательскими данными
Как проверить: docker compose up && pytest tests/test_auth.py -v
```

Как вести себя в review:

| Действие | Когда ставить | Что это значит |
|---|---|---|
| **Approve** | Всё верно, замечания закрыты | Ветка готова к merge |
| **Request Changes** | Есть блокирующая проблема: баг, дыра в изоляции, нет теста | Merge невозможен, автор чинит и обновляет PR |
| **Comment** | Вопрос или предложение без блокировки | Автор решает сам, merge разрешён |

Разница между Request Changes и Comment - не в тоне, а в последствии. Если блокирует merge, это Request Changes. Правило для нашей команды: второе касание (second touch) считается выполненным, только если ревьюер оставил хотя бы один содержательный комментарий или явно подтвердил, что всё чисто. Approve без единого замечания означает, что код не читали.

## Что ревьюер проверяет в первую очередь

Проверки в этом порядке, первые две блокирующие.

1. **Изоляция `user_id` в каждой выборке.** Любой запрос к данным должен фильтроваться по текущему пользователю. Проверяется в первую очередь, потому что утечка между пользователями - это провал проекта, а не мелкий баг:

```python
# правильно: фильтр в репозитории, а не в роуте
async def list_operations(user_id: int) -> list[Operation]:
    return await repo.list_by_user(user_id)


# неправильно: нет фильтра, любой пользователь видит чужое
async def list_operations() -> list[Operation]:
    return await session.execute(select(Operation))
```

2. **Тесты на краевые случаи прогноза.** Для EP-11 и EP-19 обязательны кейсы: нулевой доход, деление на ноль в знаменателе, единственная операция, сумма больше месяца, отсутствие категории. Прогноз без краевых случаев считается непокрытым.

3. **Отсутствие бизнес-логики в роутах.** Роут должен разобрать запрос, вызвать сервис и вернуть ответ. Если в роуте появляется `if` с арифметикой или цикл по транзакциям, это выносится в бизнес-слой. Проверяется по EP-06, EP-11, EP-17.

4. **Обработка ошибок.** Единый формат ответа: HTTP-код в статусе плюс тело `{"error": {"code": ..., "message": ..., "detail": [...]}}`. 400 на плохой ввод, 401 без токена или с чужим токеном, 404 на отсутствие и на чужой объект (403 не используется - он подтверждает существование чужой записи), 409 на конфликт, 422 на валидацию с перечнем полей в `detail`, 500 без стектрейса в теле. Необработанный `except Exception: pass` - блокирующее замечание.

5. **Отсутствие секретов в коде.** Ни паролей, ни строки подключения к БД, ни ключей подписи в репозитории. Всё через переменные окружения и `.env.example` без значений.

## CI-пайплайн

Один workflow на каждый PR, без исключений. Этапы идут последовательно, и падение любого блокирует merge.

| Этап | Команда | Что проверяет | Блокирует merge |
|---|---|---|---|
| lint-imports | `isort --check-only --diff .` | Порядок импортов | ✅ |
| lint-style | `ruff check .` | Стиль, ошибки, unused | ✅ |
| lint-types | `mypy app` | Типы (strict config) | ✅ |
| lint-security | `bandit -r app ...` | Security issues (LOW/MEDIUM/HIGH) | HIGH+HIGH confidence |
| test-unit | `pytest -q -m unit` | Unit тесты | ✅ |
| test-integration | `pytest -q -m integration` | Integration тесты | scheduled only |
| db | `alembic upgrade/downgrade/upgrade` | Миграции обратимы | ✅ |

Правила работы пайплайна:

- падение тестов на граничных случаях прогноза - блокирующее, даже если остальное зелёное;
- падение линтера чинится сразу, а не отключением правила через `# noqa` без причины в комментарии;
- покрытие 70% - общий порог для репозитория, доменные модули (лимиты, прогноз) держат 90%;
- пайплайн на каждый PR занимает до 5 минут, поэтому длинные ветки дорожают дважды: и конфликтами, и ожиданием зелёной галочки;
- `main` после merge прогоняется повторно на тех же шагах, чтобы упавший на post-merge шаг был виден сразу.

## Definition of Done

Задача считается готовой, когда выполнены все пункты:

1. Код смержен в `main`, CI зелёный.
2. Есть тесты, покрывающие основной сценарий и хотя бы один краевой случай.
3. Второе касание выполнено: second из матрицы оставил содержательный комментарий или явно подтвердил корректность.
4. Если задача меняла эндпоинт с пользовательскими данными, написан кросс-пользовательский тест: пользователь A не видит данные пользователя B.
5. Если задача трогала бизнес-логику, тесты на краевые случаи прогноза или лимитов присутствуют.
6. Валидация входных данных и коды ошибок соответствуют контракту из файла 03.
7. Секретов в коде нет, новые переменные добавлены в `.env.example`.
8. Линтер проходит без новых предупреждений.
9. README обновлён, если изменился способ запуска или добавлена новая команда.
10. Задача переведена в Done в трекере, а её роли в матрице (файл 04) отмечены выполненными.

Пункт 4 - самый важный для этого проекта. Кросс-пользовательский тест пишется всегда, когда меняется эндпоинт с пользовательскими данными, даже если кажется, что изоляция не трогалась: именно такие «мелкие» правки чаще всего ломают разделение между пользователями.

## Ceremonies Scrum

| Церемония | Когда | Длительность | Что делаем |
|---|---|---|---|
| Планирование спринта | Понедельник, 10:00 | 60 мин | Берём задачи из бэклога, сдвигаем роли, проверяем нагрузку по формуле |
| Daily | Каждый день, 10:00 | 15 мин | Три вопроса плюс «что я знаю о чужом коде» |
| Review и демо | Пятница, 16:00 | 45 мин | Показываем работающее, а не планы |
| Ретроспектива | Пятница, 16:45 | 30 мин | Что мешало, что меняем в процессе |

Календарь спринтов один на весь проект и живёт в `03` («План по спринтам»): спринт 0 - понедельник 5 октября, дальше спринты 6-9, 12-16 и 19-22 октября, по 4-5 дней, с понедельника по пятницу. Планирование спринта - понедельник 10:00, review и демо - пятница 16:00, ретро - пятница 16:45. Никаких «спринтов по неделе» отдельно от этого плана не существует.

### Планирование спринта

Порядок за 60 минут, который мы используем:

1. 5 мин - сверка с прошлым спринтом: что не закончено и почему.
2. 25 мин - выбор задач по SP с учётом коридора 12-25 SP на спринт (план спринтов из `03`: 5 / 18 / 20 / 20 SP обязательного объёма).
3. 20 мин - назначение ролей по матрице с ротацией.
4. 10 мин - проверка нагрузки по формуле: ни одна роль не выходит за 34.3 SP.
5. 5 мин - фиксация в трекере и в файле 04.

Правило: задача не берётся, если у неё нет second или если роли не сдвинулись по трём проверкам из раздела «Правила ротации».

### Review и демо

Демо в пятницу идёт по факту закрытых задач, а не по плану. Если задача не прошла Definition of Done, она не в демо, даже если выглядит почти готовой. Показываем работающий сценарий: зарегистрироваться, добавить операцию, увидеть лимит, увидеть прогноз, выгрузить отчёт.

### Ретроспектива

30 минут, три колонки: что помогло, что мешало, что меняем. Один конкретный пункт на каждое «мешало», иначе ретро превращается в жалобы. Решение фиксируется в файле 05, если это правило процесса.

## Что обсуждаем на daily

Формат «вчера / сегодня / блокеры», 15 минут, порядок ролей R1…R5, чтобы не затягивать.

1. **Вчера**: что доделал, что закоммитил, что заревьюил.
2. **Сегодня**: какую задачу берёшь и до какого состояния доведёшь.
3. **Блокеры**: что мешает прямо сейчас, кому нужно help.
4. **Что я знаю о чужом коде**: один факт о модуле другого человека.

Четвёртый пункт - обязательный и самый ценный. Формат ответа: «я знаю, что отчёт берёт операции через ScopedRepository, поэтому добавил туда поле категории, и это безопасно для лимитов». Так знание о чужом коде становится явным, а не подразумеваемым.

Правила, чтобы daily не превращался в совещание:

- говорим о задачах, а не о людях;
- блокеры решаем сразу после daily, а не в конце спринта;
- если блокер требует чужого решения, это 10 минут после daily с конкретным человеком;
- каждый раздел не больше 2 минут на человека, итого 10-12 минут чистого времени.

## Как тащим изменения в main

Рабочий цикл на одну задачу:

1. Обновить `main` локально: `git checkout main && git pull --ff-only`.
2. Создать ветку: `git checkout -b feature/forecast-formulas`.
3. Писать код, коммитить малыми частями по Conventional Commits.
4. Перед PR перебазировать на свежий `main`: `git fetch origin && git rebase origin/main`.
5. Открыть PR, дождаться зелёного CI и ревью second.
6. Merge squash-ом: `git merge --squash` в GitHub, коммит с сообщением заголовка PR.
7. Удалить ветку: `git branch -d feature/forecast-formulas`, `git push origin --delete`.

Про force-with-lease: используем только для веток, где мы единственный автор, и только с флагом `--force-with-lease`, никогда не `--force`. Порядок и правила:

- `--force-with-lease` вместо `--force` обязателен: обычный force перетирает чужие коммиты, если кто-то успел закоммитить в ту же ветку;
- в общие ветки (`main`, `develop` при его появлении) force не делается никогда;
- если ветку уже смержили и кто-то её продолжает, force запрещён: создаётся новая ветка от свежего `main`;
- перед любым force выполняется `git fetch origin`, иначе lease сравнивается с устаревшим состоянием.

Squash-merge в `main` выбран потому, что 29 задач за 18 дней дают много мелких коммитов, а в истории `main` полезнее видеть задачу, а не отдельные пробные коммиты. Локально коммиты дробные, попадают в `main` одним.

## Разрешение конфликтов

Порядок действий, когда `git rebase` или merge остановился на конфликте:

1. Не править файлы наугад: сначала посмотреть, какие файлы конфликтны, командой `git diff --name-only --diff-filter=U`.
2. Определить источник конфликта: чужой коммит из `main` или твой, и с кем обсуждать.
3. Взять решение у того, кто отвечает за домен файла, даже если это не ты.
4. Разрешить конфликт в файле, который понимаешь; остальное попросить владельца домена.
5. После разрешения продолжить: `git add <файл>` и `git rebase --continue`.
6. Прогнать тесты локально до того, как сказать «готово».

Что делать, если конфликт в чужом домене:

- не переписывать чужую логику молча, это ломает second touch;
- написать автору: «конфликт в EP-13, предлагаю оставить твою версию агрегации, вот почему»;
- если автор недоступен, взять его версию и оставить `TODO` с датой возврата, конфликт не решается «на всякий случай»;
- конфликт в миграциях (EP-01, EP-02) решается только с R1: порядок миграций менять нельзя, иначе ломается история у всех.

Частые конфликты и где они ожидаются: `models.py` и миграции (R1), роуты (R2), формулы прогноза (R3), CI-конфиг и Dockerfile (R4), шаблоны дашборда (R5). Если конфликт в файле третий раз за спринт, это сигнал пересмотреть нарезку задачи, а не поводять ещё раз перебазироваться.

## Трекер задач

Сравнение вариантов, которые мы рассматривали:

| Трекер | Цена | Ограничение при 5 людях | Вердикт |
|---|---|---|---|
| Jira Cloud Free | $0 | До 10 пользователей, наш запас есть | Выбран |
| GitHub Projects | $0 | Нет лимита, но нужна дисциплина доски | Запасной вариант |
| GitLab Free | $0 | До 5 пользователей на приватный namespace | Впритык, риск при добавлении шестого |
| Trello Free | $0 | Одна доска на бесплатном тарифе | Слабая привязка к коду |
| TODO.md в репозитории | $0 | Нет ролей, нет истории решений | Только для мелких правок |
| Задачи в Telegram-группе | $0 | Нет эпиков, спринтов, burndown и связи с PR | Для «кто что берёт сегодня», не для трекера проекта |

Выбор - **Jira Cloud Free**: бесплатно для пяти человек, есть задачи, спринты, роли и история, всё это нужно для отчётности по спринтам перед защитой.

Почему не поднимать Jira self-hosted на Railway: с 30 марта 2026 новые клиенты не могут покупать лицензии Data Center, поэтому такой инстанс уйдёт в режим read-only и перестанет быть рабочим трекером. Дополнительно self-hosted требует внешнюю Postgres, 4-8 GB RAM и имеет холодные старты, а у нас нет времени на администрирование инфраструктуры трекера в ущерб продуктовым задачам.

### Как завести доску за 20 минут

1. `atlassian.com/software/jira` → «Try Jira» на почту команды → сайт `твоякоманда.atlassian.net`.
2. **Create project** → шаблон **Scrum (company-managed)** → имя `Tachyon`, ключ `TAC`. В режиме team-managed эпиков и спринтов нет вообще, поэтому он не подходит.
3. Backlog → **Create issue → Epic**: десять эпиков `E1…E10` из `03`.
4. Внутри эпика → **Create issue → Story**. В Summary первым символом пишется плановый ключ из `04`: `EP-03 Auth: JWT, регистрация, логин`. Story Points берутся из `03`, оценки из матрицы `04` не переносятся.
5. **Create sprint**: «Sprint 0 (5 окт)», «Sprint 1 (6-9 окт)», «Sprint 2 (12-16 окт)», «Sprint 3 (19-22 окт)». Stories перетаскиваются в спринт на планировании в понедельник.
6. Board → **Add column** `In Review`. WIP-лимит: не больше одной задачи в `In Review` на человека.
7. **Workflow → Done → Validators → Require link when transitioning to Done.** Это правило DoD из этого же файла в Jira: без ссылки на PR задача не закроется.
8. Labels ролей: `primary:R3`, `second:R2`, `third:R5`. Assignee = человек с ролью primary.

Как это работает у нас: в Jira держим бэклог и статус задачи (To Do, In Progress, In Review, Done), а в файле 04 держим роли и нагрузку. Один и тот же ID задачи (`EP-03`) в обоих местах, поэтому расхождение видно сразу: задача помечена Done в Jira, но в матрице не отмечена.

Правило, которое делает доску правдивой без отдельной рутины: статус двигается вместе с git. **In Progress** ставится при начале работы, **In Review** при открытии PR, **Done** - только после merge и зелёного CI. Тогда Jira обновляется как побочный эффект работы, а не как ещё одна задача, которую надо не забыть.

## Связь

Процесс из этого документа обслуживает роли из файла 04: правило второго касания (Definition of Done, пункт 3) и есть механика ротации, выраженная в PR, а «что я знаю о чужом коде» на daily - это способ передать знание, которое иначе осталось бы у одного человека. Формула нагрузки из файла 04 проверяется на планировании спринта (шаг 4 церемонии). Оценки SP берутся из бэклога в файле 03, Jira хранит только статус, а не оценку, чтобы не было двух источников правды.

- Файл 04 (команда и роли) - роли, матрица, ротация, нагрузка.
- Файл 03 (бэклог) - оценки SP и приоритеты, из которых считается нагрузка.
