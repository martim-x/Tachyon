# 06. Стратегия тестирования

Эта стратегия отвечает на три вопроса, которые задаст себе комиссия в первую минуту защиты: что именно считается правильной работой программы, как мы доказываем, что прогноз не ломается на неполном месяце и на пустых данных, и как мы показываем, что два пользователя в одной базе не видят друг друга. ТЗ требует минимум 5 тестов на бизнес-логику, но пять тестов на счастливый путь не выдержат ни одной защиты: проверяемое комиссией поведение живёт на границах. Поэтому мы тестируем границы, а не проценты покрытия. Целевой объём: 40-60 тестов, из них минимум 20 закрывают три критичных пункта ниже. Точные числа (`48 passed`, `31 unit`, `14 isolation`) - это цель, а не факт: на защите называется реальный вывод `pytest`, поэтому цифры в `07_защита_проекта.md` проверяются по факту и корректируются в день репетиции.

## Что требует ТЗ

| Требование | Как закрываем | Где лежит |
|---|---|---|
| Python | язык реализации всего проекта | `app/` |
| Flask/FastAPI | REST API на FastAPI | `app/interface/api/` |
| SQLAlchemy + SQLite | доступ к данным | `app/core/persistence/`, `app/domains/*/models.py` |
| pandas | отчёты и агрегации | `app/domains/reporting/queries.py` |
| APScheduler | повторяющиеся операции | `app/infrastructure/scheduler.py` |
| pytest, минимум 5 тестов на бизнес-логику | `tests/unit/` + `tests/integration/` | `tests/` |
| Качество тестов | покрыты границы, а не строки | `tests/` |
| Код в репозитории | все 5 участников, коммиты по неделям | Git |
| README | запуск, архитектура, тесты | `README.md` |

Минимум 5 тестов на бизнес-логику это нижняя граница, а не цель. На защите мы показываем зелёный прогон всего набора, поэтому «5 тестов на одном модуле» выглядит слабее, чем 48 тестов с параметризацией по месяцам и пользователям.

## Три вещи, которые проверяют в первую очередь

### 1. Прогноз за неполный месяц

Это единственная часть проекта с нетривиальной арифметикой. Ошибка в ней не роняет приложение, она тихо показывает неверную цифру, и это худший вид бага для защиты. Комиссия специально смотрит, различаете ли вы 28, 29, 30 и 31 день, считаете ли вы `timedelta(days=30)` вместо длины месяца, и делите ли вы на `days_elapsed`, когда прошёл всего один день.

### 2. Нулевые траты

Первый сценарий проверки у комиссии: зарегистрировать нового пользователя, не создавать ни одной операции, пройти все эндпоинты. Ожидаемый результат: `200` с нулями и пустыми списками. Неожиданный: `500` из-за `ZeroDivisionError`, `None` в JSON или пустой файл отчёта без шапки. Пустой пользователь это состояние по умолчанию, а не исключительный случай.

### 3. Изоляция данных между пользователями

Проект многопользовательский, поэтому протечка данных это уязвимость, а не баг интерфейса. Проверка идёт по каждому домену: операции, категории, лимиты, правила повторов, отчёты, экспорт. Ключевое решение: чужой объект отдаёт `404`, а не `403`, потому что `403` подтверждает комиссии, что объект с таким id существует. Правило `user_id` в каждой доменной таблице плюс `UserContext` как единственный источник текущего пользователя закрывают путь подстановки чужого id в query.

## Формулы прогноза

> **Статус спеки (S6.1):** утверждена на бёрд-апе команды 09.10.2026 (T1-T2), зафиксирована
> в этом файле. Кейсы AC1-AC12 из таблицы выше — контракт для `tests/unit/test_forecast.py`:
> каждый тест ссылается на свой AC в docstring, ожидаемые числа берутся отсюда, а не из
> реализации. Статусы лимита (S5.2) в ядро прогноза не входят — они живут в домене бюджета.

```python
import calendar
from datetime import date
from decimal import ROUND_HALF_UP, Decimal

MONEY = Decimal("0.01")
RECENT_WINDOW_DAYS = 7
LIMIT_WARNING_RATIO = Decimal("0.8")


def money(value: Decimal) -> Decimal:
    """Приводит сумму к копейкам, округление половины вверх."""
    return Decimal(value).quantize(MONEY, rounding=ROUND_HALF_UP)


def limit_status(limit: Decimal | None, spent: Decimal, projected: Decimal) -> str:
    """Единый словарь статусов. OK < 80 %, WARNING >= 80 %, EXCEEDED - факт достиг
    или превысил лимит, EXCEEDED_PROJECTED - лимит ещё не пробит, но прогноз выше.
    Пороги включительные: ровно 80 % это WARNING, ровно 100 % это EXCEEDED."""
    if limit is None or limit <= 0:
        return "OK"
    if spent >= limit:
        return "EXCEEDED"
    if projected > limit:
        return "EXCEEDED_PROJECTED"
    if spent >= LIMIT_WARNING_RATIO * limit:
        return "WARNING"
    return "OK"


def forecast_month(
    spent_to_date: Decimal,
    year: int,
    month: int,
    as_of: date,
    *,
    pace: str = "WHOLE_MONTH",
    recent_window_total: Decimal = Decimal("0.00"),
    extra_known_amounts: Decimal = Decimal("0.00"),
    limit: Decimal | None = None,
) -> dict:
    days_in_month = calendar.monthrange(year, month)[1]
    month_start = date(year, month, 1)
    if as_of < month_start:
        # отчётный месяц ещё не начался: прошедших дней ноль, делить не на что
        days_elapsed = 0
    elif (as_of.year, as_of.month) > (year, month):
        # месяц уже закрыт: полная длина, projected равен тратам
        days_elapsed = days_in_month
    else:
        days_elapsed = min(as_of.day, days_in_month)
    days_remaining = days_in_month - days_elapsed

    if pace == "RECENT_WINDOW":
        # месяц, который не начался, темпа не даёт, даже если окно ненулевое
        if days_elapsed == 0:
            daily_rate = Decimal("0.00")
        else:
            window_days = min(RECENT_WINDOW_DAYS, days_elapsed)
            daily_rate = recent_window_total / window_days
    else:
        daily_rate = spent_to_date / days_elapsed if days_elapsed else Decimal("0.00")

    projected_total = spent_to_date + daily_rate * days_remaining + extra_known_amounts

    projected_total = money(projected_total)
    result = {
        "year": year,
        "month": month,
        "pace": pace,
        "days_in_month": days_in_month,
        "days_elapsed": days_elapsed,
        "days_remaining": days_remaining,
        "spent_to_date": money(spent_to_date),
        "daily_rate": money(daily_rate),
        "projected_total": projected_total,
        "low_confidence": days_elapsed < 3,
    }
    if limit is None:
        result["spent_percent"] = None
        result["status"] = None
    else:
        result["spent_percent"] = (
            money((spent_to_date / limit) * Decimal("100")) if limit > 0 else Decimal("0.00")
        )
        result["status"] = limit_status(limit, money(spent_to_date), projected_total)
    return result
```

### Пояснение по строкам

| Строка | Зачем так |
|---|---|
| `calendar.monthrange(year, month)[1]` | единственный источник правды о длине месяца: 28, 29, 30 или 31. `timedelta(days=30)` здесь ошибка, `monthrange` это знает с учётом високосного года |
| `month_start = date(year, month, 1)` и сравнение с `as_of` | отчёт за месяц, который ещё не начался, это штатный запрос: `days_elapsed` равен нулю, а не `.day` предыдущего месяца |
| `min(as_of.day, days_in_month)` | `as_of` может быть позже конца периода (например, отчёт за прошлый месяц при запросе сегодня). `min` не даёт выйти за длину месяца |
| `days_in_month - days_elapsed` | остаток. Равен нулю в последний день, это штатное состояние, а не особый случай |
| `if days_elapsed else Decimal("0.00")` | единственная защита от `ZeroDivisionError`. Срабатывает для будущего месяца, когда `as_of` раньше начала периода |
| `pace == "RECENT_WINDOW"` | темп считается по сумме последних 7 дней, а не по всему месяцу. `window_days` ограничен `days_elapsed`, чтобы в первый день не делить 7 дней на 1 |
| `extra_known_amounts` | суммы, которые уже известны, но ещё не записаны как операции: подтверждённая подписка, ожидаемая зарплата. Не выбрасываются из прогноза |
| `money(...)` | `Decimal` с `ROUND_HALF_UP`. `float` даёт ошибку вида `0.1 + 0.2 = 0.30000000000000004`, округление в Python по умолчанию банковское (`ROUND_HALF_EVEN`) и не совпадает с ожиданиями пользователя |
| `spent_percent` | процент расходования лимита считается по факту в денежных единицах; при `limit <= 0` возвращается 0, а не выполняется деление на ноль |
| `status` | результат `limit_status`: тот же словарь `OK` / `WARNING` / `EXCEEDED` / `EXCEEDED_PROJECTED` живёт в одной функции, статус лимита в отчёте, в эндпоинте и в тестах берётся оттуда |
| `low_confidence` | при `days_elapsed` меньше 3 прогноз статистически мусорный, но посчитать его надо. Помечаем, а не прячем |

Обе скорости обязаны быть покрыты тестами. Тест на `WHOLE_MONTH` берёт вход из таблицы краевых случаев, тест на `RECENT_WINDOW` сравнивает два числа для одних и тех же данных: 1240.00 и 1720.00.

## Нулевые траты

Сценарий проверки: зарегистрировать пользователя, не создать ни одной операции, пройти все эндпоинты его кабинета. Ни один не должен вернуть 500.

| Эндпоинт | Ожидаемый ответ |
|---|---|
| `GET /api/v1/operations?month=2026-10` | 200, `items=[]`, `total=0` |
| `GET /api/v1/operations/summary?month=2026-10` | 200, `income=0.00`, `expense=0.00`, `net=0.00`, `count=0` |
| `GET /api/v1/forecast?month=2026-10` | 200, `spent_to_date=0.00`, `daily_rate=0.00`, `projected_total=0.00`, `low_confidence=true` |
| `GET /api/v1/budget-limits?month=2026-10` | 200, `items=[]` |
| `GET /api/v1/budget-limits/status` | 200, по каждому лимиту `spent=0.00`, `spent_percent=0.00`, статус `OK` |
| `GET /api/v1/categories` | 200, `items=[]` |
| `GET /api/v1/recurring/rules` | 200, `items=[]` |
| `GET /api/v1/notifications` | 200, `items=[]` |
| `GET /api/v1/analytics/by-category` | 200, `items=[]`, `total=0.00` |
| `GET /api/v1/reports/monthly?month=2026-10&format=xlsx` | 200, валидный xlsx с шапкой и нулём строк, файл открывается |
| `POST /api/v1/operations` с некорректным телом | 422 с описанием поля, не 500 |

Дополнительно: `GET /api/v1/forecast` для месяца, который ещё не начался, и для года без данных. Ответ 200 с нулями, а не 404.

## Матрица изоляции

Правила, которые делают матрицу выполнимой:

- `user_id` типа UUID, `NOT NULL`, с индексом в каждой доменной таблице: `users`, `operations`, `categories`, `budget_limits`, `recurring_rules`, `recurring_executions`, `notifications`
- `UserContext` на базе `contextvars` как единственный источник текущего пользователя
- репозитории всегда фильтруют по `user_id`, запрос «по id» это `WHERE id = :id AND user_id = :current`
- доступ к чужому объекту отдаёт `404`, а не `403`: мы не подтверждаем существование объекта
- фильтруются не только `operations`, но и `budget_limits`, `recurring_executions`, `notifications` и агрегаты в отчётах

| Ресурс | Свой список | Чужой объект по id | Чужой `user_id` в query | Мутирующий эндпоинт |
|---|---|---|---|---|
| Операции | `GET /operations` 200, только свои | `GET /operations/{чужая_id}` 404 | `GET /operations?user_id=<чужой>` 200, фильтр игнорируется, верны свои | `PATCH /operations/{чужая_id}` 404, запись в БД не изменилась |
| Категории | `GET /categories` 200, только свои | `GET /categories/{чужая_id}` 404 | `GET /categories?user_id=<чужой>` 200, верны свои | `DELETE /categories/{чужая_id}` 404, категория на месте |
| Лимиты | `GET /budget-limits` 200, только свои | `GET /budget-limits/{чужая_id}` 404 | `GET /budget-limits?user_id=<чужой>` 200, верны свои | `PUT /budget-limits/{чужая_id}` 404, лимит прежний |
| Правила повторов | `GET /recurring/rules` 200, только свои | `GET /recurring/rules/{чужая_id}` 404 | `GET /recurring/rules?user_id=<чужой>` 200, верны свои | `POST /recurring/rules/{чужая_id}/run-now` 404, чужое правило не запущено |
| Исполнения правил | `GET /recurring/executions` 200, только свои | `GET /recurring/executions/{чужая_id}` 404 | `GET /recurring/executions?user_id=<чужой>` 200, верны свои | `DELETE /recurring/executions/{чужая_id}` 404, строка на месте |
| Уведомления | `GET /notifications` 200, только свои | `GET /notifications/{чужая_id}` 404 | `GET /notifications?user_id=<чужой>` 200, верны свои | `POST /notifications/{чужая_id}/read` 404, не прочитано |
| Отчёты | `GET /reports/monthly` 200, суммы только свои | 404 не применимо, отчёт по месяцу | `GET /reports/monthly?user_id=<чужой>` 200, цифры свои | не применимо |
| Экспорт | `GET /reports/monthly?format=xlsx` 200, 0 строк чужих данных | не применимо | `?user_id=<чужой>` 200, файл со своими данными | не применимо |

Параметризация вместо копипасты:

```python
ISOLATION_CASES = [
    ("operations", "/api/v1/operations", "/api/v1/operations/{id}"),
    ("categories", "/api/v1/categories", "/api/v1/categories/{id}"),
    ("budget_limits", "/api/v1/budget-limits", "/api/v1/budget-limits/{id}"),
    ("recurring_rules", "/api/v1/recurring/rules", "/api/v1/recurring/rules/{id}"),
    ("recurring_executions", "/api/v1/recurring/executions", "/api/v1/recurring/executions/{id}"),
    ("notifications", "/api/v1/notifications", "/api/v1/notifications/{id}"),
]


@pytest.mark.parametrize("name,list_url,item_url", ISOLATION_CASES)
def test_other_user_object_returns_404(
    api_client_a, api_client_b, factory, name, list_url, item_url
):
    obj = factory.create(name)  # объект пользователя B
    assert api_client_b.get(item_url.format(id=obj.id)).status_code == 200
    assert api_client_a.get(item_url.format(id=obj.id)).status_code == 404
```

Два теста на этот параметр (чтение и мутация) дают 12 проверок из двух функций.

## Маркеры pytest

| Маркер | Команда | Описание |
|--------|---------|----------|
| `unit` | `pytest -m unit` | Быстрые тесты без БД/сети |
| `integration` | `pytest -m integration` | Тесты с БД, миграциями, ASGI |
| `e2e` | `pytest -m e2e` | Сквозные сценарии из tests/e2e |

В CI:
- `unit` — на каждом пуше (stage `test-unit`)
- `integration` — на каждом пуше (stage `test-integration`)
- `e2e` — на каждом пуше (stage `test-e2e`)

## Структура тестов

| Директория | Что тестируем | Почему здесь |
|---|---|---|
| `tests/unit/` | чистые функции: `forecast_month`, `money`, расчёт статуса лимита, генерация дат правил повторов | нет БД и нет сети, тест идёт за миллисекунды, можно гонять сотни прогонов на защите |
| `tests/integration/` | репозитории и API на `sqlite:///:memory:` или файле в `tmp_path` | проверяем SQL, фильтры `user_id`, коды ответов, валидацию, реальные миграции |
| `tests/e2e/` | сценарий целиком: регистрация, операции, лимит, прогноз, повтор, экспорт | доказываем, что слои сшиты правильно; 2-3 сценария, не 30 |

### Что должно лежать в unit

- `test_forecast.py`: все кейсы из таблицы краевых случаев, параметризация по 12 месяцам и по високосному году
- `test_money.py`: `ROUND_HALF_UP`, отсутствие ошибок float, копейки
- `test_budget_status.py`: `OK`, `WARNING`, `EXCEEDED`, `EXCEEDED_PROJECTED`
- `test_recurrence.py`: расчёт следующих дат, месячные и недельные правила, backfill

### Что должно лежать в integration

- `test_isolation.py`: параметризованная матрица выше, 12-20 тестов
- `test_operations_api.py`: CRUD операций, коды 200, 201, 204, 404, 422
- `test_forecast_api.py`: 200 + нули для пустого пользователя и пустого периода
- `test_auth.py`: регистрация, логин, 401 без токена, 401 с чужим токеном
- `test_reports.py`: xlsx открывается, шапка есть, строки только свои

### Что должно лежать в e2e

- `test_full_flow_demo.py`: ровно тот сценарий, который показываем на защите, от регистрации до скачанного отчёта
- `test_empty_user_flow.py`: регистрация без операций и проход по всем эндпоинтам

Время без реального времени: функции прогноза принимают `as_of` параметром, а не берут `date.today()`. Планировщик запускается в тестах вручную вызовом сервиса, а не ожиданием таймера. Время подменяется через внедряемый `Clock` (в тестах `FrozenClock("2026-10-15")`), APScheduler в тестах не стартует вовсе. Тест прогноза отрабатывает за миллисекунды и не «покрасится» в марте, потому что в марте другая длина месяца.

## Фикстуры

Всё в `tests/conftest.py`, без декораторов `@pytest.fixture` в тестах.

| Фикстура | Что делает |
|---|---|
| `db_session` | поднимает схему в `:memory:` или в `tmp_path`, накатывает миграции, отдаёт сессию, откатывает транзакцию после теста |
| `clean_db` | полная изоляция: `drop_all` + `create_all` либо новая БД на каждый тест |
| `user_factory` | создаёт пользователя с уникальным email, возвращает `(user, token)`. Кеширует пользователей, чтобы не плодить их заново |
| `operation_factory` | `user_factory.operation(user=..., amount=Decimal("10.00"), date=...)`. По умолчанию сумма 10.00, чтобы тест читался как факт |
| `category_factory`, `limit_factory`, `rule_factory` | по одному объекту нужного домена на пользователя |
| `api_client` | `httpx.Client` с базой `TestClient`, принимает токен явно: `api_client(token=token_a)` |
| `api_client_a`, `api_client_b` | два залогиненных клиента под двух разных пользователей, основа всех тестов изоляции |
| `frozen_clock` | `Clock` с фиксированной датой, по умолчанию 2026-10-15 |

Правила: фикстуры не знают друг о друге по имени, только через запрос; в тесте нет строковых «магических» id; фабрики принимают `user=` первым аргументом, чтобы изоляция была видна глазом в коде теста.

## Что НЕ нужно тестировать

- Поведение сторонних библиотек: что `calendar.monthrange` возвращает 29 в високосном году проверяем мы в одном тесте и дальше доверяем библиотеке
- Формат вывода Swagger, работу pydantic-валидации на 40 полях, внутренности JWT-библиотеки
- Покрытие ради цифры. 100% покрытий достигается тестами на `__repr__` и не означает ничего. Показатель, который стоит показывать, это покрытие `app/domains/forecasting/` и `app/domains/*/repository.py`
- Каждый CRUD-метод отдельно. Для CRUD достаточно проверки контракта: код ответа, форма тела, изоляция. Одна параметризованная функция на ресурс
- Реальные внешние сервисы: отправка писем, внешние курсы валют. Если появится, интерфейс оборачивается и тестируется заглушкой
