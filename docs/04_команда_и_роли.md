# 04. Команда и роли

Этот документ отвечает на один вопрос: как пять человек за 18 дней собирают многопользовательский трекер доходов и расходов так, чтобы никто не был единственным носителем знаний о своём модуле. Здесь описаны пять ролей, матрица «задача x роли» на 29 задач бэклога, формула расчёта нагрузки, правила ротации в Scrum, разбивка по спринтам, ширина команды (bus factor) и тайминг выступления на защите. Матрица и цифры в документе не придуманы: они рассчитаны из бэклога и проверены, поэтому по ним можно планировать спринты. Порядок чтения: сначала раздел «5 ролей», потом «Матрица задача x роли», затем «Как считается нагрузка», остальные разделы нужны при планировании и накануне защиты.

Обозначения, которые используются дальше:

- **SP** (story point) - относительная сложность задачи, 1 SP = самая мелкая задача вроде правки README.
- **primary** - роль, которая делает задачу и отвечает за результат.
- **second** - роль, которая обязательно прикладывает руку: ревьюит код, пишет или правит тест, отвечает на вопросы.
- **third** - роль, которая проходит задачу бегло на этапе ревью и привлекается при сбоях.
- **R1…R5** - роли, расшифровка в разделе «5 ролей».

## Формат интерфейса: решение зафиксировано

Гейт первого дня из `01` §5 требует, чтобы выбор формата интерфейса был записан здесь и не менялся без согласия всех пяти человек. Решение принято 5 октября 2026.

| Параметр | Решение | Почему |
|---|---|---|
| Формат | веб-интерфейс поверх того же REST API | 10 баллов за удобство + место под задачу*, Swagger и ReDoc остаются как документация API |
| Серверный рендеринг | Jinja2 + HTMX поверх REST | нулевой фронтенд-сборщик, страницы открываются без `npm install`, на защите ничего не ломается из-за сети |
| SPA на React | отклонён | отдельный тулчейн, лишние 1-2 дня на сборку, на 18 днях это цена 3 баллов из 10 |
| Telegram-бот | отклонён | интерфейс должен показывать прогноз и лимиты, бот для этого хуже веб-страницы |
| Дашборд (E8) | P1, старт не раньше 19 октября и только по факту зелёного P0 | если к 19 октября фронтенд не начат, он не начинается вообще |

Разовое исключение из правила trunk-based: до 19 октября разрешена одна долгоживущая ветка `feature/dashboard`, чтобы не блокировать спринты. После решения по E8 она либо мержится, либо удаляется.

## 5 ролей

### R1 - архитектор данных

- **Зона ответственности**: ORM, модели, миграции, ScopedRepository, изоляция данных по `user_id`.
- **Навыки**: SQLAlchemy (или выбранная ORM), Alembic, проектирование схемы, понимание индексов и миграций.
- **Зеркальный резерв**: R4. Если R1 недоступен, R4 ведёт EP-01, EP-02, EP-09.
- **Чего делать не надо**: не писать бизнес-логику лимитов и прогноза (это R3), не верстать дашборд.

### R2 - API и безопасность

- **Зона ответственности**: JWT, регистрация и логин, валидация запросов, HTTP-коды, обработка ошибок, спецификация API.
- **Навыки**: REST, JWT, хеширование паролей, валидация, OpenAPI.
- **Зеркальный резерв**: R3. Если R2 недоступен, R3 закрывает EP-03, EP-04, EP-08.
- **Чего делать не надо**: не проектировать формулы прогноза, не настраивать CI и деплой.

### R3 - бизнес-логика

- **Зона ответственности**: лимиты бюджета, прогноз трат, правила повторяющихся операций, уведомления о превышении, чистое ядро без побочных эффектов.
- **Навыки**: чистые функции,Unit-тесты на краевые случаях, работа с pandas для агрегаций.
- **Зеркальный резерв**: R2. Если R3 недоступен, R2 закрывает EP-06, EP-11, EP-17.
- **Чего делать не надо**: не трогать схему миграций, не заниматься вёрсткой отчётов.

### R4 - интегратор

- **Зона ответственности**: APScheduler, CI-гейты, деплой и Docker, тестовая обвязка, Makefile, README по запуску.
- **Навыки**: GitHub Actions, Docker, Docker Compose, bash, Linux.
- **Зеркальный резерв**: R1. Если R4 недоступен, R1 ведёт EP-21, EP-24.
- **Чего делать не надо**: не проектировать доменную модель и не переписывать бизнес-правила.

### R5 - фронт и отчёты

- **Зона ответственности**: дашборд, экспорт в Excel и PDF, диаграммы, агрегация для отчётов.
- **Навыки**: шаблоны, JS или используемый фронт-стек, openpyxl, PDF-библиотека, matplotlib или аналог.
- **Зеркальный резерв**: R1. Если R5 недоступен, R1 закрывает EP-14, EP-18, EP-20.
- **Чего делать не надо**: не менять схему БД ради удобства отчёта, писать запросы в обход ScopedRepository.

## Как считается нагрузка

Нагрузка роли считается по формуле, которая учитывает реальный вклад, а не только факт «написал код»:

```
Нагрузка роли = сумма primary + 0.3 * сумма secondary + 0.08 * сумма third
```

Веса означают: secondary - это треть работы (ревью, тест, ответы на вопросы), third - почти символическое участие (беглый взгляд, подстраховка). Ревью весит втрое меньше, чем самоделка, поэтому роль не может набирать нагрузку чужими review-комментариями.

Разберём на примере роли R1:

| Состав | SP | Вес | Вклад |
|---|---|---|---|
| primary: EP-01, EP-02, EP-05, EP-09, EP-27 | 22 SP | 1.0 | 22.0 |
| secondary: EP-07, EP-10, EP-14, EP-16, EP-18, EP-21, EP-22, EP-23, EP-24 | 36 SP | 0.3 | 10.8 |
| third: EP-15, EP-20, EP-25, EP-26, EP-28, EP-29 | 17 SP | 0.08 | 1.36 |
| **Итого R1** | | | **34.16** |

Те же 0.08 дают дробь: поэтому в таблицах нагрузка округляется до двух знаков.

### Итоговая нагрузка по всем ролям

| Роль | primary SP | secondary SP | third SP | Нагрузка, SP | Доля |
|---|---|---|---|---|---|
| R1 | 22 | 36 | 17 | 34.16 | 20.0% |
| R2 | 28 | 12 | 32 | 34.16 | 20.0% |
| R3 | 27 | 19 | 20 | 34.30 | 20.0% |
| R4 | 25 | 23 | 30 | 34.30 | 20.0% |
| R5 | 22 | 34 | 25 | 34.20 | 20.0% |
| **Сумма** | **124** | **124** | **124** | **171.12** | **100%** |

Разброс суммарной нагрузки между ролями - 0.41% от среднего, то есть роли почти не отличаются по загрузке за весь проект. При этом структура нагрузки разная: у R2 и R3 больше своя работа, у R1 и R5 больше участия в чужих задачах. Это нормально и полезно: чем больше у роли second-работы, тем лучше она знает чужой код.

Обратная сторона: у каждой роли ровно 124 SP в secondary/third-сумме, поэтому ротация не может сделать нагрузку одной роли выше 34.3 без перераспределения в чужую зону. Напоминание: эти 124 SP - распределение работы по ролям, а не план сдачи. План сдачи - обязательный объём 63 SP из `03`.

| R2 и R4 | 8 |

Минимум 7 выдержан для всех десяти пар. Ни одна пара ролей не изолирована: любой человек может быть подменён любым другим, если тот знаком с доменом.

### Норма нагрузки

Норма нагрузки считается от плана спринтов в `03`: обязательный объём 63 SP разложен на спринты 5 / 18 / 20 / 20 SP при 5 людях, то есть примерно 3-4 SP на человека на спринт. Отклонение выше 25 SP на спринт означает, что в спринт втянули лишнее (и это повод выполнить шаг лестницы сокращений), ниже 12 SP - риск недогруза, который лечится добавлением задач из резерва. Значение «40 SP на спринт» из предыдущей редакции документа неверно: это вдвое больше, чем весь обязательный объём проекта, и оно же породило расхождение 124 SP против коридора 60-66 SP.

## Правила ротации

1. **Один primary на задачу.** Задача закреплена за одним человеком, secondary и third не делят ответственность, но участвуют.
2. **Обязательный second touch в Definition of Done.** Задача не закрыта, пока second не подтвердил второе касание: ревью, тест или ответ на вопрос. Если second не может, роли меняются на этапе планирования спринта.
3. **Лимит 30% времени на ревью.** Роль не должна тратить больше 30% рабочего времени на чужие задачи. Формула это уже ограничивает вкладом 0.3 и 0.08.
4. **Роли сдвигаются на планировании спринта.** На каждом планировании берётся новая ротация: роли, которая недавно была second, поднимается в primary на своей следующей задаче, а не остаётся в second навсегда.
5. **Ревью до 40 минут и обязано содержать архитектурный вопрос.** Если ревью идёт дольше 40 минут, задача нарезана неверно: её надо разделить и переоценить.
6. **Daily в формате «что я знаю о чужом коде».** Кроме трёх стандартных вопросов каждый называет один факт о чужом модуле. Это механизм передачи знаний, который заменяет документацию.
7. **Правило подмены выбывшего.** Если человек выбывает, его задачи переходят зеркальному резерву по умолчанию, а вторичные роли переходят primary-роли выбывшего на ближайших его задачах. Неделя на передачу знаний, затем роли перебалансируются на планировании.

### Как ротация выглядит на практике

Ротация - это не перестановка людей по списку, а правило, по которому вторая роль становится первой на следующей задаче того же домена. Ниже - как это выглядит на домене R3 (бизнес-логика):

| Задача | Primary | Second | Что это даёт |
|---|---|---|---|
| EP-06 лимиты | R3 | R5 | R5 впервые смотрит доменную логику |
| EP-11 прогноз | R3 | R2 | R2 понимает формулы, чтобы не сломать API |
| EP-19 тесты прогноза | R3 | R2 | R2 пишет тесты на свой же контракт |
| EP-13 отчёт | R3 | R2 | R2 видит, как данные идут наружу |

На следующем витке EP-11 и EP-13 уходят в primary на R2 и R5 соответственно, если те готовы. Именно так знание о формулах перестаёт быть личным.

Проверка ротации на планировании спринта задаётся тремя вопросами, и если хотя бы один ответ «нет», задача в спринт не берётся:

1. Есть ли у задачи second, который способен взять её, если primary выбывает прямо сейчас?
2. Не превысит ли second суммарно 30% своего времени на ревью?
3. Был ли этот second на предыдущей задаче того же домена? Если нет, а ротация давно не сдвигалась, меняем роли именно сейчас.

### Управляемый перекос в спринте 1

В спринте 1 у R2 16.64 SP против 5.80 SP у R4. Это не ошибка балансировки, а следствие стартовой позиции:

- на старте один человек закрывает auth плюс CRUD, потому что без них нельзя сделать ни одного работающего эндпоинта;
- инфраструктура (CI, Docker, деплой) в спринте 1 ещё не нужна: её нечего гонять, пока нет фич, и она естественно уходит в спринт 3;
- прогноз (EP-11) нужен рано, потому что формулы определяют модель данных, поэтому он поставлен в спринт 1, хотя остальная доменная логика идёт во втором.

**Процедура выравнивания**, чтобы перекос не превратился в перегрузку:

1. R2 в спринте 1 не берёт задачи сверх EP-03 и EP-04 плюс ревью; всё остальное переносится в спринт 2.
2. R4 получает EP-07 и EP-22 в спринте 1 как «лёгкий старт» и переносит EP-21, EP-23, EP-24 в спринт 3, где они и по плану.
3. На планировании спринта 2 вторичные роли R4 (EP-10, EP-19) дают R4 разгон, а R2 постепенно уходит с первенства.
4. Если R2 показывает на daily, что не успевает EP-03 или EP-04, EP-08 переезжает в спринт 3 без обсуждения: это приоритетная задача с двумя другими ролями, справится быстрее.
5. Фактическая проверка - разница R2 и R4 по итогам спринта 1 должна быть в коридоре 8-14 SP. Больше - переносим; меньше - R4 берёт вторую роль в задачах домена R2.

По спринтам 2 и 3 перекос уходит в другую сторону (R5 и R4 поднимаются, R2 и R1 опускаются), поэтому суммарно нагрузка выровнена. Это и было целью ротации.

## Bus factor и риски схемы

| Риск | Признак | Митигация |
|---|---|---|
| Уход человека с уникальным модулем | Задача без second, который реально прикасался к коду | Правило second touch в DoD, минимум 7 общих задач у пары |
| Монокнопотенциал на auth | EP-03 и EP-04 оба на R2, second сразу перегружен | R3 зеркальный резерв, EP-03 и EP-04 разнесены по ролям second/third |
| Знание уходит из CI | EP-24 на R4 без ревью от домена | R1 ведёт second/third по инфраструктуре, EP-28 кросс-ревью |
| Ревью превращается в формальность | second ставит Approve не читая | Правило 40 минут и архитектурный вопрос в каждом ревью |
| Ротация без фактической передачи знаний | Роли меняются, но код никто не знает | Daily «что я знаю о чужом коде», парные задачи в одном спринте |
| Bus factor = 1 на отчётах | EP-13, EP-14, EP-18, EP-20 распределены тонко | У каждой задачи отчётов second из R1 или R2, минимум 7 общих задач |
| Срыв дедлайна из-за «экспорта в PDF» | Бонусные задачи отнимают время у основных | EP-16 и EP-18 помечены как бонус, идут после основных в спринте 3 |
| Перегрузка на ревью к концу | Кросс-ревью копятся в последнюю неделю | По одной задаче кросс-ревью в спринт, EP-25…EP-29 распределены |

Полный bus factor команды - 1 в худшем случае (уход одного человека роняет один модуль), но не 0: ни один модуль не остаётся без двух других ролей, которые его трогали. Реалистичная цель - пережить уход любого одного человека без остановки разработки больше чем на один день.

## Равномерность на защите

Защита 24-25 октября: телемост, 7 минут демо плюс 2-3 минуты вопросов. Демо делится на пять слотов по 420 секунд, чтобы ни одна роль не говорила «ну и так понятно».

| Слот | Роль | Время | Что показывает |
|---|---|---|---|
| 1 | R1 | 65 с | Схема данных и изоляция по user_id |
| 2 | R2 | 60 с | Auth, регистрация, ошибки и коды |
| 3 | R3 | 100 с | Лимиты, прогноз, повторяющиеся операции |
| 4 | R4 | 95 с | Планировщик, CI, деплой |
| 5 | R5 | 100 с | Дашборд, экспорт, диаграммы |
| **Всего** | | **420 с** | 7 минут |

Правило блока: **каждый в конце своего слота обязан назвать модуль, который ревьюил**. Это не формальность, а проверка того, что вторая роль действительно работала. Формулировка простая: «модуль X я ревьюил как second, и вот что поправил». Если назвать нечего, значит second touch был фиктивным, и это видно сразу.

Подготовка к таймингу:

- репетиция с секундомером за два дня до защиты, один прогон;
- демо запускается на заранее поднятом стенде, а не на локальной машине;
- у каждого есть своя ветка с коммитом, который показывается, чтобы при сбое переключиться на соседний модуль;
- резервный сценарий: если R4 не успел показать деплой, он показывает README и health-эндпоинт, это те же 95 секунд.

- Файл 05 (процесс разработки) - как роли взаимодействуют в git: ветки, PR, ревью, Definition of Done.
