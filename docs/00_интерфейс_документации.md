# 00. Интерфейс документов Tachyon

Этот файл - вход в каталог `docs/`. Он не содержит требований и не содержит кода: он объясняет, какой файл открывать по какому вопросу, где лежит каждое поле правды и что было решено 5 октября. Начать отсюда, потом идти по маршруту R1-R5.

Файлов девять: `00` (этот) и `01`-`08`. `01` и `02` отвечают на вопрос «что делаем и как устроено», остальные - производные от них.

Проверено 5 октября 2026: числа и код из документов исполнялись, а не пересказывались. Что именно - в разделе «Проверено числами».

## 2. Маршруты чтения

**R1. Первый день, ничего не знаю.** этот файл → `01` §1 и §5 → `02` §1-2 → `05` §1-2 → гейт первого дня (раздел 4). После этого есть минимальный набор решений, которого хватает, чтобы открыть первый PR.

**R2. Хочу понять архитектуру.** `02` целиком. Ключевое: `app/core` → `app/domains/<домен>/{api,service,repository,models}.py` → `app/interface` и `app/infrastructure`. Слои ТЗ («данные, бизнес-логика, интерфейс») реализованы дословно внутри каждого домена. Прогноз живёт в `forecasting` без единого импорта SQLAlchemy.

**R3. Хочу понять план.** `03` (что делаем) → `04` (кто делает) → `08` (в каком порядке по неделям). Числа обязаны сходиться: полный бэклог 92 SP, обязательный объём 63 SP, резерв 3 SP, P0 67 / P1 12 / P2 13.

**R4. Хочу понять процесс.** `05` целиком. Ветка + PR + ревью + Jira + Telegram + DoD. `06` - приложение к `05`: там про то, что именно проверяем.

**R5. Готовлюсь к защите.** `07` целиком, потом `06` (числа для финала демо), потом `01` (критерии, под которые нас оценивают).

## 4. Решения, принятые 5 октября

Раньше эти восемнадцать пунктов были противоречиями между файлами. Теперь это зафиксированные решения; поменять можно только здесь и обсудив командой.

| # | Что было спорно | Решение | Где живёт |
|---|---|---|---|
| 1 | три структуры папок: слои против доменов | домены: `app/{core,domains,interface,infrastructure}`, 7 доменов | `02` §1-2, `03` S1.1, `08` неделя 1 |
| 2 | три системы ID: `E1…E10`/`S1.1…S10.2`, `EP-01…EP-29`, недельные списки | внешний ID - `EP-01…EP-29`. `E#/S#` - внутренняя история бэклога, на Jira не выгружается | `03` шапка, `04`, `05` §3 |
| 3 | объём: 59 SP против 60-66 SP против 124 SP | обязательный объём 63 SP, коридор 60-66, резерв 3 SP. 124 SP - это распределение работы по ролям, не план сдачи | `03` шапка, `04` §6 |
| 4 | порог 80 %: `>` против `>=` | включительно: `fact >= 0.8 × limit` даёт `WARNING`. 79 % - `OK`, 80 % - `WARNING`, 100 % - `EXCEEDED` | `01` §3.3, `03` S5.2, `06` таблица |
| 5 | словарь статусов: `ok/warn/exceeded`, `none/normal/warning/exceeded`, `OK/WARNING/EXCEEDED` | `OK`, `WARNING`, `EXCEEDED`, плюс `EXCEEDED_PROJECTED` для прогнозного превышения. Других значений в проекте нет | `01` §3.3, `03` S5.2, `06` `limit_status()` |
| 6 | деньги в БД: `Integer`, `Numeric(12,2)`, `Numeric(14,2)` | SQLite: целые копейки в `Integer`. Домен: `Money` на `Decimal`, округление `ROUND_HALF_UP`, сравнения только в денежных единицах. Причина: колонка `NUMERIC` под SQLite физически хранится как `REAL`, то есть как `float` | `02` §5, `03` S1.1, `07` вопрос «Как округляете деньги» |
| 7 | формат ошибки: `{"detail": ...}` и `{"error": {...}}` | HTTP-статус в статусе ответа плюс тело `{"error": {"code", "message", "detail"}}`. Чужой объект по прямому ID - 404, не 403 | `02` §6, `05` §5, `08` |
| 8 | прогноз на неполном месяце: 12 кейсов проходили, 13-й ломался | месяц, который ещё не начался: `days_elapsed = 0`, темп 0, `low_confidence = true`. Сравнение с началом месяца, а не взятие `.day` | `06` `forecast_month()` |
| 9 | достижение лимита: `>` против `>=` | факт, **равный** лимиту, - это `EXCEEDED`. Прогнозное превышение - отдельный статус | `06` `limit_status()` |
| 10 | маршруты лимитов: `/limits` против `/budget-limits` | `/api/v1/budget-limits`, `/api/v1/budget-limits/status`, `/api/v1/budget-limits/{category_id}` | `01` §1.5, `02`, `03` S5, `06`, `08` |
| 11 | маршруты повторов: `/recurring`, `/recurrences`, `/recurring/rules` | `/api/v1/recurring/rules`, `/api/v1/recurring/rules/{id}`, `/api/v1/recurring/rules/run` | `01` §1.5, `02`, `03` S4, `06` |
| 12 | маршруты отчётов: `/reports/month`, `/reports/monthly`, `/reports/summary` | `/api/v1/reports/monthly`, `/api/v1/reports/monthly/export?format=excel\|pdf`, `/api/v1/forecast`, `/api/v1/reports/by-category` | `01` §1.5, `02`, `03` S6 |
| 13 | модель повторов: `Recurrence(...template_operation)` и `recurring_rules(kind, amount, schedule, last_run_at)` | `RecurringRule` / таблица `recurring_rules`: `kind daily\|weekly\|monthly`, `interval`, `start_date`, `end_date`, `category_id`, `amount_cents`, `note`, `next_run_at`, `is_active`, `last_run_at`. | 14 | поля операции: `type/date/comment` | `Operation`: `kind income\|expense`, `amount_cents`, `occurred_at`, `note`, `source`, `recurring_execution_id` | `02` §3, `03` S1.1, `08` |
| 15 | `S9.2` был одновременно снимаемым и обязательным, `S9.3` снимался без шага | `S9.2` и `S9.3` неснимаемы, входят в 63 SP. Лестница сокращений - 4 шага на 4 SP: `S6.4` → `S4.5` → `S6.3` → `S9.5` | `03` §«Лестница сокращений» |

## 5. Проверено числами

**`04`, матрица ролей.** 29 задач, сумма 124 SP. primary 22/28/27/25/22, second 36/12/19/23/34, third 17/32/20/30/25 - каждая колонка даёт 124. Нагрузка по формуле `1.0 / 0.3 / 0.08` = 34.16 / 34.16 / 34.30 / 34.30 / 34.20. Спринты 41 / 39 / 44 SP, нагрузки по ролям внутри каждого спринта сходятся с таблицей. У всех десяти пар ролей минимум 7 общих задач. Пример разбора роли R1 в `04` переписан под фактические списки.

**`03`, бэклог.** Сумма эпиков 92 SP (7+10+8+13+8+11+10+8+12+5), P0 = 67, P1 = 12, P2 = 13. Обязательный объём 63 SP - это 67 минус 4 SP снятых на старте, снятые задачи сгруппированы и лестница пронумерована.

**`06`, код из документа исполнен как есть.** `forecast_month()` против своей таблицы краевых случаев: 12 прогнозных кейсов совпали после починки будущего месяца (до починки - 11 из 12), плюс 4 граничных кейса общего блока. `limit_status()` против 8 наборов аргументов - 8 совпали. Контрольные значения 1240.00 / 600.00 / 0.00 / 1446.67 совпадают во всех трёх формулах, описанных в `01`, `02`, `03`, `06`.

**Остальное.** Вычищены ссылки на несуществующий каталог `документы/`, старые пути `app/api`, `app/services`, `app/db`, `app/scheduler`, `app/reports`, старые маршруты, `Numeric(...)` в моделях, `will_exceed_limit`, числа ревизий Alembic и расхождения по числу тестов. Числа тестов теперь помечены как цель, а не как факт: на защите называется реальный вывод `pytest`.

## 6. Правило одного поля правды

Одно поле правды - в одном файле. Если нужно изменить формулу, маршрут, поле модели или словарь статусов: правим сначала раздел 4 здесь, потом один файл-владелец, потом `grep` по остальным восьми. Не наоборот.

| Поле | Файл-владелец | Производные |
|---|---|---|
| требования ТЗ и критерии баллов | `01` | все файлы |
| схема данных, структура папок, маршруты, формат ошибки, деньги | `02` | `03`, `06`, `07`, `08` |
| оценки SP, приоритеты, план спринтов, лестница | `03` | `04` (нагрузка), `05` (лестница в DoD), `08` |
| роли, зоны, нагрузка, формат интерфейса | `04` | `05` (роли в PR), `07` (тайминг) |
| процесс, ветки, PR, ревью, трекер, DoD | `05` | `04`, `03` |
| формулы прогноза, 22 краевых случая, числа тестов | `06` | `02` (дубль формулы), `07` (числа на демо), `08` |
| сценарий защиты и ответы комиссии | `07` | - |
| раскладка по неделям и чек-лист сдачи | `08` | `03` (объём) |

Правило одной правки: изменил `01` - в тот же день правишь `02` (слои или сущности) и `03` (объём); изменил `02` - правишь дерево папок в том же файле, контракты границ в `05` и кейсы в `06`; изменил `03` - пересчитываешь нагрузку в `04`; изменил `06` - пересчитываешь числа в `07` и `08`.
