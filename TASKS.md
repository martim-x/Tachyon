работы. Общие правила проекта (изоляция данных, деньги, код-стайл, DoD) — в
`docs/`, ссылки внизу.

**Правило главное: журнал дописывается, а не перезаписывается.** Ты не
затираешь чужие строки и не переписываешь свою строку на другую — дописываешь
новую в конец. По журналу видно, кто и когда что делал.

## 2. Журнал

Один файл, один блок на задачу, внутри — список строк. Агент дописывает
свою строку в конец блока. Чужие строки не трогаются, свои не удаляются.

Формат строки:

```
- 2026-10-21 23:15 — в работе (Агент А), ветка `feature/reporting-aggregation`
- 2026-10-21 23:41 — готов к ревью (!24)
- 2026-10-21 23:55 — смержено
```

Знаки: `свободна` — можно брать; `в работе (<кто>)` — взята; `готов к ревью
(<MR>)` — код написан, ждёт CI; `смержено` — MR в `main`.

**Текущий статус задачи — последняя строка её блока.** Раньше лежавшая строка
`в работе` не означает, что задача занята, если ниже уже есть `смержено`.

**Освободил задачу — допиши строку `свободна`, а не убери старую.** Журнал
append-only: по нему видно историю. Если задачу взял ты, а потом снял с себя —
допиши `свободна`.

## 3. Как взять задачу

1. **Проверь, не занята ли.** Смотри свежее состояние, не локальную копию:
   ```bash
   git fetch origin --prune
   glab mr list --search "TT-26"     # открытый Draft MR = задача занята
   git show origin/main:TASKS.md     # журнал: последняя строка блока
   ```
   Журнал живёт в `main` только после мержа, поэтому признак занятости —
   **открытый Draft MR**: его видно всем сразу. Ищи MR по ID задачи, он
   написан в описании MR.

2. **Создай ветку от свежего `main`:**
   ```bash
   git checkout main && git pull --ff-only origin main
   git checkout -b feature/<домен>-<описание>
   ```
   Имя — латиница и дефисы, без номеров задач, дат и `-v2`.

3. **Заклейми задачу Draft MR — до того как начнёшь писать код.** `main`
   запрещён для прямых коммитов, клейм в него не положить:
   ```bash
   # дописать свою строку в конец журнала блока своей задачи
   git add TASKS.md
   git commit -m "chore(agents): отметить TT-xx в работе"
   git push origin feature/<домен>-<описание>
   glab mr create --draft --source-branch feature/<домен>-<описание> \
     --target-branch main --title "<имя ветки без префикса>" \
     --description "Задача: TT-xx (<название>). Клейм: работа начата."
   ```
   Строка журнала едет в том же MR и станет видна всем после мержа.

4. **Если по задаче уже есть чужой Draft MR — откажись.** Ничего в журнал не
   пиши: строка «отказ» сделала бы последнюю строку блока не «в работе», и
   следующий агент не понял бы, занята задача или нет. Просто закрой свой
   Draft MR и бери другую задачу.

5. **Зависимость не смержена — код не пиши.** TT-27/29/31/33 ждут TT-26.
   Дублировать чужой код нельзя.

6. **Конфликт в блоке журнала при merge — не всегда проигранная гонка.**
   Второй агент мог дописать `готов к ревью` или `свободна`, а не `в работе`.
   Посмотри, что стоит в конфликтующих строках: если там нет `в работе`, твой
   клейм не проиграл — перечитай журнал и продолжай. Обе строки в конфликте
   оставь: историю не переписывают.

## 4. Окружение и гейт

Каждый агент — в **своём worktree**, иначе агенты мешают друг другу:

```bash
git worktree add ~/.hermes/cache/scratch/wt-<своё-имя> -b feature/<...> origin/main
cd ~/.hermes/cache/scratch/wt-<своё-имя>
cp .env.example .env          # в worktree нет .env, без него import падает
python3 -m venv .venv && .venv/bin/python -m pip install -e ".[dev]"
```

Python — 3.11 или 3.12. На 3.9 проект не ставится: pip отклоняет его с
ошибкой `requires a different Python: 3.9.6 not in '>=3.11'`.

**Гейт перед push — все семь команд зелёные:**

```bash
.venv/bin/python -m ruff check .
.venv/bin/python -m mypy app
.venv/bin/python -m bandit -r app -c pyproject.toml -ll -iii
.venv/bin/python -m pytest
.venv/bin/python -m alembic upgrade head
.venv/bin/python -m alembic downgrade base
.venv/bin/python -m alembic upgrade head
```

Тот же набор гоняет `.gitlab-ci.yml` (7 jobs). Одна красная — push не делать.

- **Не добавляй `-q` второй раз.** В `pyproject.toml` уже `addopts = "-q"`, и
  `-qq` прячет строку «N passed» — набор выглядит пустым, хотя зелёный.
- **Тесты не собрались — это провал, а не успех.** Проверь число:
  `pytest --collect-only | tail -2`.

## 5. Коммит, MR, готово

**Коммит.** Conventional Commits: `<тип>(<домен>): <что сделано в прошедшем
времени>`. Одна логическая единица — один коммит. Тело содержательное: что
нашёл, в чём корень, как чинил, какие тесты. `Co-Authored-By` не проставлять.

**Push.** В GitLab, затем в GitHub — зеркало:
```bash
git push origin feature/<...>
git push github feature/<...>
```

**MR.** Название = имя ветки без префикса типа. Описание: что сделано, зачем,
как проверить локально, ID задачи. Открывай сразу **Draft** — это клейм.
Когда код готов к ревью — `glab mr update <iid> --ready` и допиши в журнал
строку `готов к ревью (<MR>)`.

Мержить MR не надо — это делает тимлид после зелёного CI.

**Замечания Duo.** Проверяй по репозиторию до правок — Duo ошибается. Ложное:
ответ с доказательством и `resolved=true` без правок. Подтверждённое: фикс →
ответ с хешем коммита → `resolved=true`. Проверка:
```bash
glab api "projects/87278857/merge_requests/<iid>/discussions?per_page=100"
```

**Готово, когда:** гейт зелёный локально; CI на ветке зелёный (7/7); тест на
изоляцию данных для любого нового эндпоинта с пользовательскими данными;
фикстуры — в `tests/conftest.py`, `@pytest.fixture` в тестах запрещён;
`requirements.txt` пересобран, если менялись зависимости
(`uv pip compile pyproject.toml --extra dev --universal --output-file requirements.txt`);
MR открыт, нерешённых замечаний нет; в журнал дописана строка `готов к ревью`.

## 7. Что нельзя

- Менять код в чужой ветке, чужом MR или в чужом форке без явной просьбы
- Мержить MR самостоятельно
- Править чужой `.env`; в worktree — только `cp .env.example .env`
- Коммитить `.env`, `tachyon.db`, `bandit-report.json`, логи
- Дублировать код агрегации, который уже реализован в TT-26
- Отключать правила линтера через `# noqa` без причины в комментарии
- `pip freeze` для `requirements.txt` — только `uv pip compile`
