## 2. Журнал

Один блок на задачу, внутри — список строк. Агент дописывает свою строку в
конец блока, чужие не трогает, свои не удаляет.

```
- 2026-10-21 23:15 — + в работе (Агент А), ветка `feature/reporting-aggregation`
- 2026-10-21 23:41 — готов к ревью (!24)
- 2026-10-21 23:55 — смержено
```

Знаки: `свободна` — можно брать; `+ в работе (<кто>)` — взята, идёт
реализация; `готов к ревью (<MR>)` — код написан, MR открыт и ждёт CI и
ревью; `смержено` — MR в `main`. **Плюс — главный знак:** он и означает
«задача в разработке».

**Статус задачи — последняя строка её блока.** Старая строка `+ в работе` ниже
не значит «занято», если под ней уже `смержено`.

**`смержено` пишет тимлид** — отдельным MR после мержа, потому что агент не
мержит (§5) и дописать в `main` не может. Пока этой строки нет, признак
смерженной задачи — MR в списке merged: `glab mr list --merged --search
"TT-26"`.

**Освободил задачу — допиши `свободна`, а не убери старую строку.** По журналу
видно историю.

## 3. Как взять задачу

1. **Проверь, не занята ли.** Смотри свежее состояние, не локальную копию:
   ```bash
   git fetch origin --prune
   glab mr list --search "TT-26"     # открытый Draft MR = задача занята
   git show origin/main:TASKS.md     # журнал: последняя строка блока
   ```
   Журнал в `main` появляется только после мержа, поэтому признак занятости —
   **открытый Draft MR**: его видно всем сразу. Ищи MR по ID задачи — он
   написан в описании MR.

2. **Ветка от свежего `main` — через worktree (§4).** Не делай
   `git checkout main`: в основном worktree `main` уже заcheckout, и команда
   падает с `fatal: 'main' is already checked out at ...`. Ветку создаёт
   `git worktree add ... -b feature/<...> origin/main` — она сразу от свежего
   `origin/main`, отдельный checkout не нужен. Имя — латиница и дефисы, без
   номеров задач, дат и `-v2`.

3. **Заклейми задачу Draft MR — до того как начнёшь писать код.** `main`
   запрещён для прямых коммитов, клейм в него не положить:
   ```bash
   # дописать свою строку в конец журнала блока своей задачи
   git add TASKS.md
   git commit -m "chore(agents): отметить TT-xx в работе"
   git push origin feature/<домен>-<описание>
   glab mr create --draft --source-branch feature/<домен>-<описание> \
     --target-branch main --title "<имя ветки без префикса>" \
     --description "Задача: TT-xx (<название>). Клейм: работа начата."
   ```
   Строка журнала едет в том же MR и станет видна всем после мержа.

4. **Если по задаче уже есть чужой Draft MR — откажись.** Ничего в журнал не
   пиши: строка «отказ» сделала бы последнюю строку блока не «+ в работе», и
   следующий агент не понял бы, занята задача или нет. Закрой свой Draft MR и
   бери другую задачу.

5. **Зависимость не смержена — код не пиши.** TT-27/29/31/33 ждут TT-26.
   Проверь сам, а не по журналу:
   ```bash
   glab mr list --merged --search "TT-26"   # пусто = TT-26 ещё не в main
   ```
   Строка `смержено` в журнале появляется только когда тимлид допишет её
   отдельным MR после мержа, поэтому признак смерженной зависимости —
   **MR в списке merged**, а не строка журнала. Строка `готов к ревью (!24)`
   в `main` означает, что MR **уже смержен**: строка едет в том же MR с
   кодом, и в `main` попадает только вместе с ним. Состояния «в `main` и
   ждёт CI» не бывает.

6. **Конфликт в блоке журнала — не всегда проигранная гонка.** Второй агент
   мог дописать `готов к ревью` или `свободна`, а не `+ в работе`. Если в
   конфликтующих строках нет `+ в работе`, твой клейм не проиграл — перечитай
   журнал и продолжай. Обе строки оставь: историю не переписывают.

## 4. Окружение и гейт

Каждый агент — в **своём worktree**, иначе агенты мешают друг другу:

```bash
git worktree add ~/.hermes/cache/scratch/wt-<своё-имя> -b feature/<...> origin/main
cd ~/.hermes/cache/scratch/wt-<своё-имя>
cp .env.example .env          # в worktree нет .env, без него import падает
python3 -m venv .venv && .venv/bin/python -m pip install -e ".[dev]"
```

Python — 3.11 или 3.12. На 3.9 проект не ставится: pip отклоняет его с
ошибкой `requires a different Python: 3.9.6 not in '>=3.11'`.

**Гейт перед push — все семь команд зелёные** (тот же набор, что в
`.gitlab-ci.yml`, 7 jobs):

```bash
.venv/bin/python -m ruff check .
.venv/bin/python -m mypy app
.venv/bin/python -m bandit -r app -c pyproject.toml -ll -iii
.venv/bin/python -m pytest
.venv/bin/python -m alembic upgrade head
.venv/bin/python -m alembic downgrade base
.venv/bin/python -m alembic upgrade head
```

Одна красная — push не делать.

- **Не добавляй `-q` второй раз.** В `pyproject.toml` уже `addopts = "-q"`, и
  `-qq` прячет строку «N passed» — набор выглядит пустым, хотя зелёный.
- **Тесты не собрались — это провал, а не успех.** Проверь число:
  `pytest --collect-only | tail -2`.

## 5. MR и «готово»

Открывай MR сразу **Draft** — это клейм. Когда код готов к ревью:
`glab mr update <iid> --ready` и допиши в журнал `готов к ревью (<MR>)`.
Мержить MR не надо — это делает тимлид после зелёного CI. После мержа тимлид
дописывает в журнал строку `смержено` отдельным MR — агент дописать её не
может, в `main` коммитить запрещено. Имя MR, формат коммита и полный DoD — в
`docs/05_процесс_разработки.md`.

Замечания Duo проверяй по репозиторию до правок — Duo ошибается. Ложное:
ответ с доказательством и `resolved=true` без правок. Подтверждённое: фикс →
ответ с хешем коммита → `resolved=true`.

```bash
glab api "projects/87278857/merge_requests/<iid>/discussions?per_page=100"
```

**Готово, когда:** гейт зелёный локально; CI зелёный (7/7); тест на изоляцию
данных для нового эндпоинта с пользовательскими данными; фикстуры — в
`tests/conftest.py`, `@pytest.fixture` в тестах запрещён; `requirements.txt`
пересобран, если менялись зависимости (`uv pip compile pyproject.toml
--extra dev --universal --output-file requirements.txt`); MR открыт,
нерешённых замечаний нет; в журнал дописана строка `готов к ревью`.
