## 1. Доска задач

Каждой задаче — свой блок. Блок описывает **неизменную** часть задачи (что делать,
где, от чего зависит), а **меняемую** часть — журнал.

**Журнал дописывается, а не перезаписывается.** Каждый агент, взявший задачу,
дописывает в конец журнала свою строку. Прежние строки не трогаются: по ним видно
историю — кто, когда и на каком этапе был у задачи. Последняя строка журнала —
текущий статус.

Правила знаков (в каждой строке журнала):

| Знак | Значит |
|---|---|
| `свободна` | задачу можно брать |
| `+ в работе (<кто>)` | задача взята, идёт реализация |
| `готово к ревью (<MR>)` | код написан, MR открыт, ждёт зелёного CI |
| `✓ смержено` | MR смержен в `main` |

Строка журнала пишется в таком виде:

```
- 2026-10-21 23:12 — свободна
- 2026-10-21 23:15 — + в работе (Hermes, основной агент), ветка `feature/reporting-aggregation`
```

Дата и время — локальные, формат `ГГГГ-ММ-ДД ЧЧ:ММ`. Ветку агент выбирает сам
(§2.2), поэтому она пишется в строку журнала, а не в блок задачи.

## 2. Как взять задачу

1. **Прочитай журнал, а не заголовок.** Журнал блока — источник правды о том,
   кто задачу уже взял. Клейм агента лежит в `main` (§2.3), поэтому смотри
   свежий `origin/main`, а не локальную копию:
   ```bash
   git fetch origin --prune
   git log origin/main --oneline -- AGENTS.md
   git show origin/main:AGENTS.md
   ```
   В журнале задачи уже есть строка `+ в работе (...)` — задача занята, бери
   другую. Пустая строка `свободна` — можно брать. Дополнительно проверь, что
   по задаче нет открытого Draft MR: `glab mr list --all`.
2. Создай ветку от свежего `main`:
   ```bash
   git fetch origin --prune
   git checkout main && git pull --ff-only origin main
   git checkout -b feature/<домен>-<краткое-описание>
   ```
   Формат имени — `<тип>/<домен>-<описание>`, латиница и дефисы. Номера задач,
   даты, версии (`-v2`) и номера эпиков в имени ветки **запрещены**.
3. **Заклейми задачу в `main` — отдельным коммитом, до того как начнёшь писать код.**
   Клейм должен быть виден всем сразу: если он лежит только в ветке агента, второй
   агент возьмёт ту же задачу, пока работа не закончится.
   ```bash
   # дописать свою строку в конец журнала блока своей задачи в AGENTS.md
   git add AGENTS.md
   git commit -m "chore(agents): отметить TT-xx в работе"
   git push origin main
   ```
   Push отклонён (другой агент запушил раньше) — `git pull --rebase origin main`
   и повторить. Конфликт при rebase в своём блоке означает, что задачу уже
   кто-то взял: посмотри журнал, сними свой клейм, бери другую задачу.
4. Если в поле «Зависит от» указан номер, который ещё не смержен, — **не начинай
   писать код**. Дождись, пока зависимость смержится, и только потом переходи к
   своей задаче. Дублировать чужой код нельзя: см. §4. То же относится к
   обратному полю «Блокирует»: если твой номер стоит там у другой задачи, эта
   задача ждёт тебя.

## 3. Окружение и гейт

Каждый агент работает в **своём worktree** — иначе агенты мешают друг другу в
общем рабочем дереве:

```bash
git worktree add ~/.hermes/cache/scratch/wt-<своё-имя> -b feature/<...> origin/main
cd ~/.hermes/cache/scratch/wt-<своё-имя>
cp .env.example .env          # в worktree нет .env, без него import падает
```

`DATABASE_URL=sqlite+aiosqlite:///./tachyon.db` относительный — у каждого worktree
своя БД, конфликта не будет. Проверено 2026-10-21: worktree подхватывает свой `app`,
а не код основного репозитория.

Установка зависимостей (в репозитории `.venv` уже есть, но он указывает на основной
репозиторий — в worktree нужен свой):

```bash
python3 -m venv .venv && .venv/bin/python -m pip install -e ".[dev]"
```

Версия Python — 3.11 или 3.12. На 3.9 проект не ставится: pip отклоняет его
с ошибкой `requires a different Python: 3.9.6 not in '>=3.11'` (в
`pyproject.toml` `requires-python = ">=3.11"`), а без fastapi не поднимается и
`import app.main`.

**Полный гейт перед push — все семь команд должны быть зелёными:**

```bash
.venv/bin/python -m ruff check .
.venv/bin/python -m mypy app
.venv/bin/python -m bandit -r app -c pyproject.toml -ll -iii
.venv/bin/python -m pytest
.venv/bin/python -m alembic upgrade head
.venv/bin/python -m alembic downgrade base
.venv/bin/python -m alembic upgrade head
```

Это ровно тот набор, что гоняет `.gitlab-ci.yml` (7 jobs). Если хотя бы одна
команда красная — код не готов, push не делать.

Два правила, которые ломаются чаще всего:

- **Не добавляй `-q` второй раз.** В `pyproject.toml` уже `addopts = "-q"`. Двойной
  `-q` (`-qq`) прячет строку «N passed» — набор выглядит пустым, хотя зелёный.
- **Тесты не собираются — считай это провалом, а не успехом.** Проверь фактическое
  число: `pytest --collect-only | tail -2`. На текущем `main` — 183 теста
  (67 unit + 112 integration + 4 e2e).

## 4. Жёсткие правила кода

Это не пожелания, а то, за что Duo снимает баллы, а комиссия — репутацию.

**Изоляция данных (15 баллов защиты).** Любая выборка данных фильтруется по текущему
пользователю. Фильтр — в репозитории, а не в роуте:

```python
# правильно
async def list_operations(user_id: uuid.UUID) -> list[Operation]:
    return await repo.list_by_user(user_id)

# неправильно
async def list_operations() -> list[Operation]:
    return await session.execute(select(Operation))
```

Выборки — только через `ScopedRepository`. Доменный сервис не дублирует проверку
владения FK — это делает сам `ScopedRepository`.

**Деньги.** Только `Decimal` + `ROUND_HALF_UP`, в БД — целые копейки. `float` запрещён.
Конвертация `Money` ↔ копейки — только в репозитории (`to_money()`,
`Money.from_cents()`), API-слой колонку `amount_cents` не трогает. Доли в процентах
тоже `Decimal`, без float.

**Ошибки.** HTTP-код в статусе плюс тело `{"error": {"code": ..., "message": ..., "detail": [...]}}`.
400 — плохой ввод, 401 — нет токена или чужой токен, **404 на чужой объект (403 не
используется — он подтверждает существование чужой записи)**, 409 — конфликт,
422 — валидация с перечнем полей в `detail`, 500 — без стектрейса в теле.
`HTTPException` inline запрещён — использовать `NotFound`, `PermissionDenied` из
`app.core.errors`.

**Слои.** Роут разбирает запрос, вызывает сервис, возвращает ответ. Если в роуте
появляется `if` с арифметикой или цикл по транзакциям — это выносится в
бизнес-слой. `app/interface/export/` — адаптеры: они знают только DTO, домены
про xlsx/pdf не знают.

**Одна функция агрегации.** NFR-3 в TT-26/27/29/31/33: отчёт, экспорт и диаграмма
используют один и тот же код агрегации. Дублировать pandas-логику в адаптерах
запрещено — правка потом разойдётся по трём местам.

**Никаких `print`** — только `logging`. Никаких секретов в коде: всё через
переменные окружения, `.env` в `.gitignore`.

**`read-only` для reporting.** В `app/domains/reporting/` не должно быть
`session.add` и `commit`.

## 5. Коммиты, push, MR

**Коммит.** Conventional Commits: `<тип>(<домен>): <что сделано в прошедшем времени>`.
Одна логическая единица — один коммит: если в описании нужно слово «и», это два
коммита. Тело содержательное: что нашёл, в чём корень, как чинил, какие тесты.
Пустые тела не принимаются. `Co-Authored-By` не проставлять.

**Push.** В GitLab, затем **обязательно** в GitHub — зеркало:

```bash
git push origin feature/<...>
git push github feature/<...>
```

Если пайплайн не запустился автоматически: `glab pipeline run --branch <...>`.

**MR.** Название MR = имя ветки без префикса типа (`feature/export-excel` →
`export-excel`). Описание — три строки: что сделано, зачем, как проверить локально,
плюс ID задачи (`EP-14`). Мержить MR **не надо** — это делает тимлид после
зелёного CI.

**MR нельзя мержить, пока в нём есть нерешённые замечания Duo.** Проверка:

```bash
glab api "projects/87278857/merge_requests/<iid>/discussions?per_page=100"
```

Каждое замечание проверяй по репозиторию до правок — Duo ошибается. Ложное
замечание: ответ с доказательством и `resolved=true` без правок. Подтверждённое:
фикс → ответ с хешем коммита → `resolved=true`.

## 6. Definition of Done

Задача сдана, когда выполнено всё:

- [ ] Все семь команд гейта (§3) зелёные локально
- [ ] CI на ветке зелёный (7/7 jobs)
- [ ] Кросс-тест на изоляцию данных для любого нового эндпоинта с пользовательскими данными
- [ ] Имена тестов содержат ключевое слово для `-k`-селекторов (`-k isolation`, `-k forecast`, `-k empty`)
- [ ] Все фикстуры в `tests/conftest.py`; `@pytest.fixture` в тестах запрещён
- [ ] `requirements.txt` пересобран, если менялись зависимости:
      `uv pip compile pyproject.toml --extra dev --universal --output-file requirements.txt`
- [ ] MR открыт, нерешённых замечаний нет
- [ ] В журнал задачи (§1) дописана строка `готово к ревью (<MR>)`

### Что делать с зависимостями

`pyproject.toml` — источник правды; `requirements.txt` собирается из него.
**CI ставит зависимости из `pyproject.toml`** через `pip install -e ".[dev]"`,
а `requirements.txt` используется только при ручной установке по README.
Поэтому пайплайн **не ловит** рассинхронизацию манифеста — это уже случалось
21 октября: забытый `apscheduler` сломал «запуск с нуля», а CI был зелёный.
Пересобирай манифест в том же коммите, где меняешь зависимости.

## 8. Что нельзя

- Менять код в чужой ветке, чужом MR или в чужом форке без явной просьбы
- Мержить MR самостоятельно
- Править чужой `.env`; в worktree — только `cp .env.example .env`
- Коммитить `.env`, `tachyon.db`, `bandit-report.json`, логи
- Дублировать код агрегации, который уже реализован в TT-26
- Отключать правила линтера через `# noqa` без причины в комментарии
- `pip freeze` для `requirements.txt` — только `uv pip compile` (иначе теряются
  платформенные маркеры и установка ломается на Windows)
